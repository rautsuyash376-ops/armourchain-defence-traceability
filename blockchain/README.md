# Defence Equipment Traceability dApp — Smart Contracts

**Status:** proposed interface v0.1; local implementation and tests are being prepared. This repository is not yet team-approved, deployed, audited, or production-ready.

This package provides a Solidity smart contract for registering equipment and spare parts, two-step custody transfers, maintenance and inspection records with approval, audit trail events, asset-status changes, and off-chain document integrity hashes. It uses OpenZeppelin `AccessControl` and `Pausable`.

> **Operational security:** MST is a public chain. Keep classified and sensitive operational information, asset serials, exact unit/site locations, personal data, maintenance narrative, photographs, PDFs, and all full documents off-chain in approved access-controlled storage. Put only opaque identifiers, hashes, limited status metadata, and role-controlled wallet addresses on-chain. A hash proves a later byte-for-byte match; it does not prove the source document is truthful or authorized. This prototype has not received an independent security audit and must not be used for classified or safety-critical workflows without security, legal, and operational approval.

## Fresh clone setup

Requirements: Node.js 20+ (tested target: Node 22), npm, Git.

```bash
npm install
cp .env.example .env
npm run compile
npm test
npm run export:abi
```

The contract uses Solidity 0.8.24, optimizer enabled (200 runs), EVM target Cancun, and OpenZeppelin Contracts 5.0.2. Exact direct dependency versions are pinned in `package.json`. A package lock could not be generated in this environment because the npm registry was unreachable; generate and commit `package-lock.json` by running `npm install` in the team environment before treating the dependency graph as frozen.

Generate opaque IDs for records off-chain:

```bash
node scripts/generate-asset-id.cjs
```

Do not generate asset IDs by hashing serial numbers or low-entropy sensitive fields: public hashes can be guessed. Generate random `bytes32` values and map them to operational identifiers in your approved backend database.

## Interface coordination gate

The API in `docs/API_CONTRACT.md` is a **proposal**, not evidence that frontend/backend developers have approved it. Before freezing the ABI, share the API document, confirm all indexed event fields and ID formats with those developers, and update the document with named approvals. Notify the team before any function signature, role, event, field ordering, or enum change. A change that affects the ABI should be treated as a coordinated interface change and reviewed through a pull request.

## Deployment safety

The deployment scripts verify the connected chain ID, require a signer, and write the actual mined transaction hash, contract address and block to the corresponding file in `deployments/`. Mainnet deployment additionally requires a specific authorization flag, an approval reference, an allowlisted deployer address, and an explicitly configured minimum balance. A Mainnet RPC endpoint must also be configured first. These guards do not replace human authorization or a security review.

**Actual deployment / PR status for this prepared workspace:** no network deployment was run; the deployment records remain `NOT_DEPLOYED`. The local Git branch is `feature/defence-equipment-traceability`. The remote repository URL, existing team changes, named reviewers, and required GitHub approvals were not available, so no remote push or pull request is claimed.
